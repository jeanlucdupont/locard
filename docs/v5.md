# Locard V5: derived forensic reports

Locard V5 is application version **0.6.0**, Apache-2.0, with evidence schema **3**
unchanged. Reporting is optional and adds no runtime dependencies. Existing V0–V4
commands remain available independently. Reports are sensitive derived outputs;
the original evidence remains authoritative.

**AI-generated narrative does not create forensic facts. Semantic similarity does
not create forensic facts. A detection alone does not prove compromise. Absence of
matching evidence does not prove that an event did not occur. Report hash validation
checks file integrity, not the truth of forensic conclusions.**

## Generate, inspect, and validate

The destination must be a **new directory under an existing parent**. Use a private
case-output directory outside the source repository. The case must already be
schema 3; reporting never creates or migrates an evidence database.

```powershell
# Deterministic report of explicitly selected records; repeat --evidence as needed.
locard --db C:\Cases\Example\case.db report generate `
  --evidence '<original-evidence-id>' `
  --output C:\Cases\Example\reports\selection-01

# One or more V4 investigations with the exact same evidence fingerprint.
locard --db C:\Cases\Example\case.db report generate `
  --investigation '<investigation-id>' `
  --transcript-root C:\Cases\Example\investigations `
  --profile technical --redact none `
  --output C:\Cases\Example\reports\investigation-01

# Optional local-model assistance; factual text is still rendered by Locard.
locard --db C:\Cases\Example\case.db report generate `
  --evidence '<original-evidence-id>' --profile executive --redact identifiers `
  --llm-narrative --endpoint http://127.0.0.1:8080 `
  --output C:\Cases\Example\reports\sharing-01

locard report show C:\Cases\Example\reports\selection-01
locard report validate C:\Cases\Example\reports\selection-01
locard report validate C:\Cases\Example\reports\selection-01 `
  --case C:\Cases\Example\case.db
locard report validate C:\Cases\Example\reports\investigation-01 `
  --case C:\Cases\Example\case.db `
  --transcript-root C:\Cases\Example\investigations
```

`--evidence` and `--investigation` are mutually exclusive. Up to eight same-state
investigations can be combined. Identical claims are deduplicated, retaining every
origin; differing hypotheses remain separate. Mixed fingerprints, unsupported
transcripts, dry runs, unfinished transcripts, and missing support are rejected.

An explicit-ID report records `input_mode: explicit_evidence_ids` in report data,
methodology, manifest, and HTML. It covers the supplied records and required support
only. It performs no new investigative search, detection run, or model tool loop.
Empty finding categories are **not investigative negative results**. Inventory and
timeline enrichment are identified as report-time operations, not prior model work.

Optional analyst metadata: `--title`, `--case-name`, `--case-identifier`,
`--analyst-name`, `--organization`, and `--scope-note`. Each value is limited to
1,000 UTF-8 bytes, escaped, and labeled analyst-supplied rather than evidence.

## Claims and traceability

The eight explicit categories are:

| Category | Authority and meaning |
| --- | --- |
| OBSERVED FACT | Controller-selected field, revalidated against the case; compact-field omissions remain visible |
| DETERMINISTIC RELATIONSHIP | Existing engine object, supporting records, and original status |
| CORROBORATED RELATIONSHIP | Existing engine object with its unchanged CORROBORATED status |
| DETECTION | Existing versioned rule observation; severity is review priority, not compromise probability |
| MODEL/ANALYST HYPOTHESIS | Unverified proposal, cited records, alternatives, and explicit verification gaps |
| CONFLICT | Structured incompatible context assertions; no competing assertion silently wins |
| UNKNOWN | Unresolved engine relationship or explicitly unverified model-proposed unknown |
| LIMITATION | Scope, partial investigation, omitted data, or other recorded caveat |

Claim IDs are hashes of category, structured assertion, and supporting evidence IDs.
Origins are accumulated separately. JSON includes forward/reverse evidence mappings,
engine objects and their claim mappings, and conflict qualification edges. This is
a provenance graph, not a new correlation engine. Similarity scores are never
promoted to evidence, confidence, relationships, or conclusions. V5 does not infer
semantic contradictions between arbitrary hypothesis prose; unverified proposals
remain separate and their verification gaps remain visible.

V4 observed facts are rebuilt from the exposure ledger. A retrieved record is not
automatically a model-exposed record. Exposure describes a request attempt, not an
attestation of receipt. Required support, including Registry containing keys, must
be present. Report-time additions are not attributed to the model.

## Historical transcripts and evidence grounding

The adapter supports transcript format 1, policy `v4-1`, schema 3, and application
versions 0.5.0/0.6.0. It applies bounded strict JSON parsing, hash-chain checks,
event-order checks, exposure reconstruction, and controller rendering of final
findings. It then compares historical compact projections to current case fields
and recomputes exposed deterministic engine objects. Unsupported objects or changed
case contents fail closed.

This is deliberately separate from V4 exact-code replay. The adapter does not
claim that a changed application reproduces a historical model conversation.
Recorded semantic candidates can have their deterministic expansions checked
without the embedding model or index. Historical semantic retrieval itself is not
rerun or independently authenticated. A transcript with recomputed hashes can be
forged; case grounding checks observations, not the authenticity of operation history.

Methodology distinguishes completed operations from attempts lacking a result.
Parser versions and model identities are reported only where recorded. Missing
metadata remains missing. Local server model names are self-reported, not weight
attestations. Full transcripts are not copied into report bundles; preserve them
separately under the case's access controls.

## Timeline, inventory, and profiles

Timeline rows preserve original evidence ID, slot, original timestamp value,
normalization, precision, source, and meaning. MFT SI and FN observations stay
separate. Registry last-write belongs to the key, not value creation; inherited
observations reference their owning key and are deduplicated by key/slot. Prefetch
retained execution slots do not constitute a complete execution history. Unknown
or unnormalizable timestamps are not assigned invented UTC times.

The inventory covers referenced source files, with hashes, recorded parser and
extractor versions, ingestion history, and stored record counts. Counts do not
mean the model examined every record. `source_locations` is authoritative for all
observed acquisition paths; `events.source_file` retains its ingestion-path meaning.
Acquisition paths are omitted unless `--include-source-locations` is supplied with
`--redact none`. Evidence-derived paths may still appear in unredacted findings.

Both profiles include metadata, summary, scope, inventory, methodology, questions,
findings, timeline, hypotheses/conflicts/unknowns/limitations, conclusions, evidence
references, and investigation provenance. `executive` shortens factual detail and
shows up to 50 timeline entries in HTML. All included claims remain in JSON;
material caveats remain visible. Neither profile permits unrestricted model prose
to supply factual conclusions.

## Optional narrative assistance

The default is fully deterministic, without MiniCPM or semantic packages. The
optional local-model call receives up to 20 validated claims in a 5,600-byte prompt.
It can return only an ordered list of supplied claim IDs. Locard validates the
closed response, rejects duplicate/invented IDs and additional prose, and renders
the facts itself. All mandatory caveats remain regardless of the ordering.

There is one request, no tools or investigation loop, no repair loop, and a maximum
45-second call within the report deadline. The existing loopback-only HTTP client
rejects nonlocal endpoints, redirects, and proxy use. Failure produces a deterministic
report with `COMPLETE_WITH_LIMITATIONS`. Prompt hash, configuration, response status,
and available model metadata are disclosed separately from deterministic report data.

## Redaction and sensitive handling

`none` preserves selected values; acquisition paths are still omitted by default.
`identifiers` is intentionally conservative:

- All observed assertion values and sensitive field payloads become consistent
  report-local aliases, including usernames, hosts, IPs, paths, commands, scripts,
  Registry data, and unrestricted evidence text.
- Questions, hypothesis prose, free-text warnings/reasons, analyst metadata,
  locators, and model/index identity metadata are suppressed where appropriate.
- Controlled categories, qualifying cautions, omission counts, source hashes,
  original evidence IDs, normalized timestamps, and numeric metadata remain.
- The same policy applies to JSON, HTML, and manifest, before optional model input.
  No unredacted alias crosswalk is emitted. Redacted claim IDs are recomputed.

This reduces disclosure; **it is not anonymization**. Original IDs/hashes permit
linkage, and timestamps/counts can be identifying. Redaction does not modify evidence
or transcripts. Free-text limitations may require review in the unredacted report.
Do not assume any generated report is suitable for public release without review.

## Bundle, integrity, and validation

| File | Purpose |
| --- | --- |
| `report.json` | Structured report, claims, evidence, graph, and provenance |
| `report.html` | Escaped standalone HTML with embedded static CSS and print styling |
| `manifest.json` | Report identity, fingerprint, input hashes, mappings, and JSON/HTML SHA-256 hashes |
| `checksums.sha256` | SHA-256 of the preceding three files; no self-hash |

HTML has no JavaScript, web server, external resources, analytics, remote fonts, or
active evidence-derived links. A restrictive CSP supplements escaping. JSON and
HTML rendering are cross-checked during validation. There is no automatic PDF or
Markdown exporter and no browser/PDF runtime dependency. HTML can be printed manually.

Validation reports four separate results:

1. **File integrity**: bounded files and checksum agreement.
2. **Structure**: format, claims, graph, manifest references, and matching HTML rendering.
3. **Case fingerprint**: optional comparison with an explicitly selected case.
4. **Evidence grounding**: deterministic reconstruction from that case and, for
   investigation reports, the original transcripts. Redacted reports validate the
   redacted projection; they do not recover hidden values.

Missing case/transcripts leave the applicable check `NOT_CHECKED`; they never
produce a grounding PASS. `conclusions_truth` is always `NOT_ESTABLISHED`. Replacing
an entire bundle and recomputing its checksums defeats unauthenticated integrity
checks; retain an external trusted checksum if replacement detection is required.
Hashes are not signatures. Report format 1 requires a compatible V5 renderer.

Canonical deterministic data and stable claim IDs are reproducible for the same
case, inputs, options, and implementation. Report UUID, creation time, optional
model ordering, and complete output-file hashes are not expected to be identical.
A dedicated report-diff command and cryptographic signing are deferred.

## Bounds, consistency, and publication

| Bound | Default / ceiling |
| --- | --- |
| Claims, including limitation summary | 100 / 1,000 |
| Timeline section observations | 500 / 5,000 |
| Direct evidence inputs | 1,000 |
| Hydrated records including required support | 2,000 |
| Input investigations | 8 |
| Generation deadline | 300 / 600 seconds |
| Worker operation | 45 seconds |
| Worker message / memory | 512 KiB / 2 GiB |
| Structured data / individual output / entire bundle | 16 MiB / 32 MiB / 64 MiB |

Use `--max-claims`, `--max-timeline`, and `--seconds` within these ceilings. Material
conflicts and unknowns are reserved ahead of ordinary findings; generation fails
if mandatory caveats cannot fit. Omission counts are explicit. Timeline bounds
apply to the timeline section; individual hydrated record projections also retain
their timestamp metadata within the overall size bounds.

The worker uses the existing schema-3 read-only opener, SQLite authorizer, and short
per-operation snapshots. Fingerprinting and collection share each transaction.
No snapshot is retained during model waits. Changed fingerprints, 64 MiB of WAL
growth during an operation, deadlines, and worker failures stop publication.
Windows parent-owned jobs terminate the actual Python worker, including when the
virtual-environment executable is a launcher; a worker-owned job retains memory limits.

Publication uses a private sibling staging directory, exclusive file creation,
flush/fsync, bundle verification, and same-volume directory rename. Existing
destinations and symlink/reparse-point paths are rejected. Failures remove the
current staging directory where possible; abrupt host termination can leave an
ignored staging directory, never a deliberately published partial bundle. This is
not a guarantee against a compromised host or filesystem/power-loss behavior.

- `COMPLETE`: the requested bounded report finished, not a complete forensic examination.
- `COMPLETE_WITH_LIMITATIONS`: usable output with explicit omissions, partial input,
  warnings, or failed optional narrative assistance.
- `FAILED`: grounding, compatibility, consistency, resource, or publication failure;
  no new final report directory is published.

## Validation record

Final accumulated result: **266 tests passed** in the regular environment and
**266 tests passed** in the isolated core-only environment (Windows, Python 3.12.14).

All ordinary tests use generated synthetic data and mocked model responses. The
suite covers rehashed transcript/report forgery, case changes, context conflicts,
Registry support, scoped direct selection, multiple investigations, HTML escaping,
redaction, publication failure, worker timeout/termination, WAL pressure, and optional
model rejection. The full accumulated suite is run after each major implementation
stage. Live MiniCPM checks remain separate and use synthetic evidence only.

The accumulated suite also passes in an isolated core-only Python environment
without sentence-transformers, FAISS, PyTorch, Transformers, NumPy, Hugging Face Hub,
Tokenizers, or Safetensors. A saved 0.5.0 investigation was separately consumed by
0.6.0 reporting and passed evidence grounding. A conceptual semantic-history fixture
verifies deterministic expansion without installing its historical embedding model.

Two local live checks accepted 12 ordered claim IDs each, with unredacted and
identifier-redacted inputs; both generated reports passed evidence grounding.
Prompt sizes were 5,011 and 5,037 bytes. This demonstrates contract interoperability,
not forensic interpretation quality or general model reliability.

The reproducible manual benchmark is `python tests/v5_benchmark.py OUTPUT_ROOT CLAIMS`.
It creates 625 synthetic MFT records and 5,000 timestamp observations. Windows,
Python 3.12.14 measurements (single runs; timings vary with concurrent load):

| Claims | Generate | Grounding validation | Hash files | JSON / HTML | Parent / actual worker peak working set |
| --- | --- | --- | --- | --- | --- |
| 100 | 11.17 s | 10.99 s | 0.042 s | 5.61 / 2.47 MB | 98.2 / 30.4 MiB |
| 1,000 | 11.50 s | 10.15 s | 0.030 s | 6.37 / 3.09 MB | 103.1 / 30.2 MiB |

Both retained 5,000 timeline entries and passed grounding. Claim omissions correctly
produced `COMPLETE_WITH_LIMITATIONS`. Whole-case fingerprinting is included and may
dominate on large cases. These are synthetic measurements, not capacity guarantees.

No new dependencies were added. Apache-2.0 and existing third-party notices are
unchanged. `.gitignore` continues to deny unapproved file types and excludes report
bundles, evidence, databases, transcripts, model/index data, and staging directories.
Only source, synthetic fixture generators, tests, and documentation belong in Git.
