# EVTX numeric-array compatibility (6.70)

Locard's `forensic_assistant/ingest/evtx_arrays.py` provides a minimal,
source-controlled extension to the pinned python-evtx 0.8.1 decoder. The
substitution traversal and XML renderer are adapted from upstream Apache-2.0
code, with its copyright/license notice retained. No installed package is
modified, no process-global monkeypatch is installed, and no dependency changes
are required. `evtx_recovery.Record` uses this subclass through the existing
validated record-boundary path.

Only numeric array substitution types 0x84, 0x88, 0x8A, 0x94 and 0x95 are added.
Values are little-endian unsigned integers. Windows comparison establishes
unsigned decimal rendering or lowercase, unpadded `0x` hexadecimal rendering,
and repetition of the containing XML element for each item (one empty element for an empty array). Arrays are not
joined into a string. The supported element shape has one array substitution
as its sole content; unvalidated mixed/attribute array positions fail explicitly.
Scalar conversion and XML escaping continue to use upstream behavior.

Lengths must be nonnegative, divisible by element width, and within the mapped
buffer, chunk data, enclosing record payload and enclosing length-delimited
BinXML payload. Unsupported types still raise; malformed data is not skipped.
Existing chunk CRC, record framing, hashing, normalization, provenance and
300-second deadline behavior are unchanged.

The header assessment in `evtx_recovery.py` uses the existing supported structural
checks (major 3, minor 1 or 2, magic and header sizes) together with the actual
header checksum, rather than upstream's minor-version-1-only `verify()`.
Malformed/unsupported structures remain rejected; checksum failure still produces
an explicit diagnostic and follows the existing recovery policy. Chunk/bounds
checks remain independent.

## Validation and limitations

Synthetic tests: `tests/test_evtx_arrays.py`; existing recovery/ingestion and
identifier tests remain authoritative. The dirty-tail test now expects its real
tail diagnostic without a false version-3.2 header warning.

Opt-in Windows comparison: set `LOCARD_EVTX_ACCEPTANCE_DIR` to an authorized
copy directory, then run `tests/test_evtx_arrays_acceptance.py`. This reads copies
and invokes `wevtutil` read-only with explicit Unicode output. No real EVTX or
case database is stored in the repository. Four selected complete records are
compared for array element values/order, provider and event identifiers; the
0x88 sample's decoded array is compared separately because a subsequent 0x86
substitution still fails. A complete WMI control log must produce byte-identical
XML to upstream.

Newly exposed limitation: the selected NTFS 0x88 record also contains unsupported
0x86 (unsigned 16-bit array), producing `KeyError: 134`. This is intentionally
outside the five-type patch; no claim of complete NTFS recovery is made.
CertificateServices nested BinXML, deadline accounting, nonstandard event-trace
formats, and other unvalidated array shapes/types remain unresolved.

Validation: 64 focused synthetic/recovery/ingestion tests passed, and
7 opt-in Windows acceptance checks passed. The latter includes the explicit
known-0x86-failure assertion, not a claim that the full 0x88 sample renders.
Real-copy checks also confirmed that all 35 CertificateServices decoding failures
remain explicit, and a nonstandard trace file remains rejected.


## Full copied-log scan results

Direct decoding plus XML well-formedness validation (not deadline-limited ingestion):

| Log | Before XML successes | After XML successes | Total | Remaining error |
| --- | ---: | ---: | ---: | --- |
| Intel graphics external | 0 | 101514 | 101514 | none |
| System | 37694 | 37803 | 37803 | none |
| NTFS Operational | 14902 | 15493 | 16449 | 956 KeyError: 134 |
| Hyper-V Hypervisor Admin | 113 | 226 | 226 | none |

All four input SHA-256 hashes were unchanged. Scan times including XML
well-formedness validation were 374.55, 129.61, 238.64 and 0.55 seconds,
respectively. These do not guarantee completion under the unchanged ingestion
deadline. The subsequent empty-array rendering correction preserves Windows'
empty elements; it does not change successful-record counts.

NTFS recovers 587 previously failing 0x8A records and four records with empty
0x88 arrays. The other 956 records expose unsupported 0x86. Thus the requested
five-type decoder extension is present, but complete NTFS recovery remains
blocked on a separately scoped type extension.
