# Locard V4 controlled investigation

Application 0.5.0; evidence schema 3. V4 is optional and introduces no evidence
migration or runtime dependency. Locard remains Apache-2.0; existing third-party
terms and notices are unchanged. V0 ingestion, V1 correlation, V2 artifacts and V3
retrieval remain independently available. V4 requires an existing schema-3 case;
its read-only opener never creates or upgrades a database.

**THE LLM DOES NOT EXECUTE COMMANDS. THE LLM DOES NOT QUERY THE DATABASE DIRECTLY.**
**THE LLM REQUESTS PREDEFINED READ-ONLY FORENSIC OPERATIONS. LOCARD VALIDATES AND
EXECUTES THOSE OPERATIONS. MODEL HYPOTHESES ARE NOT FORENSIC EVIDENCE.**

## Operation

```powershell
locard --db data\case.db investigate-ai 'Inspect PowerShell activity' --no-semantic --json
locard --db data\case.db investigate-ai 'Inspect registry persistence' --semantic-index data\case.db.semantic-index --embedding-model data\semantic-models\bge --explain
locard --db data\case.db investigate-ai 'Inspect PowerShell activity' --max-steps 4 --max-tool-calls 2 --max-seconds 180 --approve-tools
locard --db data\case.db investigate-ai 'Inspect PowerShell activity' --dry-run
locard --db data\case.db investigation show '<investigation-id>' --explain
locard --db data\case.db investigation replay '<investigation-id>' --no-semantic
```

`--db` precedes the command. `--transcripts` chooses an explicit derived-data root;
the default is `DATABASE.investigations`. IDs are generated UUID hex strings.
`--endpoint` accepts only HTTP numeric loopback (with localhost normalized), using
the existing llama.cpp client. There are no proxies, redirects, cloud calls, DNS
enrichment, external programs selected by the model, or evidence acquisition tools.
The loopback model server is a separate trusted operator-managed application: secure
its configuration and logs. Evidence sent to it remains sensitive.

Initial retrieval reuses V3's deterministic/hybrid planner. No grounded starting
records means no unconstrained model plan. A fresh bounded prompt is built per
turn. The model returns either one tool proposal or one structured final selection.
The bounded prompt includes explicit action examples, allowed argument names and
completed-operation notices; the server's grammar is not assumed to explain the
action contract to the model. Continuations distinguish completed work from the
original question's first-action instruction.
The controller validates unknown/missing fields, exact types (booleans are not
integers), bounds, duplicate JSON keys, nonfinite values, anchor syntax, disclosure,
active-case membership and applicable tools. It does not repair invalid requests.

V4 dry-run executes initial retrieval, calls the local model once, validates and
displays the proposal, and stops without executing an iterative operation. Invalid
first proposals are recorded without a retry. `ask --dry-run` retains its existing
no-model behavior. Approval mode is optional, rejects noninteractive input, defaults
to refusal, and includes time waiting for approval in the investigation deadline.

## The nine tools

| Tool | Existing API / meaning | Bound |
|---|---|---|
| `search_evidence` | Common evidence SQL filters, combined with AND; at least one required | 50 records |
| `semantic_search` | Local V3 candidate search, then existing deterministic expansion of at most five anchors | 20 hits, 50 resulting records |
| `show_evidence` | Known original evidence ID, selected compact fields | One record plus required supporting records |
| `timeline` | Timestamp observations with original meanings, explicit start/end | 24 hours, 50 records |
| `around` | Same-host temporal neighbors; explicit slot needed for ambiguous times | 3,600 seconds, 50 records |
| `process_tree` | Existing conservative EVTX parent/child reconstruction | 6 levels, 50 nodes |
| `session` | Existing successful-logon anchored correlation | 24 hours, 50 records |
| `detections` | One installed rule ID from the frozen source-controlled registry | 25 findings, 100 initial candidates |
| `investigate_evidence` | Existing cross-artifact investigation/statuses | 3,600 seconds, 50 candidates |

Tool input schemas are in `investigation_ai/contracts.py`; the fixed dispatch is in
`tools.py`. Outputs share a bounded envelope: tool name, deterministic/semantic
behavior, records with original IDs, engine relationships, detections, limitations,
returned count, truncation flag, semantic candidates and the untrusted-evidence label.
Relations/detections are omitted when their required support cannot travel with them.
Not every original/raw field is exposed: use existing `show --raw` outside V4 when
necessary. Timestamp meanings, truncation notices, evidence IDs and engine statuses
are retained. Returned records are deduplicated by original evidence ID.

Process and session tools are advertised only when appropriate known evidence exists.
Semantic tools are advertised only after the worker has successfully loaded its
local semantic capability; a precise initial plan can remain deterministic-only for
that run. Optional dependencies are never necessary for `--no-semantic` operation.
Models cannot choose case paths, model paths, index paths, endpoints, output paths,
SQL, executables, plugins, or new detection rules. Scope is the selected case;
allowlisted searches can explore other records within that case, not another case.

## Evidence authority and prompt injection

All forensic content is inside a distinct `UNTRUSTED FORENSIC EVIDENCE` JSON section.
Controller instructions are separate. Delimiters alone do not prevent model
influence: hostile Registry values, script text, command lines and filenames may
still influence which permitted operation the model proposes or when it stops.
The allowlist, case boundary, budgets and finding validation remain authoritative
even if the model follows those instructions. These controls do not guarantee a
complete investigation or eliminate misleading model hypotheses.

State tracks retrieved IDs, selected IDs and actually disclosed fields separately.
Only the last category is citable. An observed finding selects an original ID and
a JSON-pointer field, such as `/process_name`; Locard renders the exact disclosed
value, timestamp semantics, warnings, support IDs and truncation qualifiers.
It does not accept model-authored observed-fact sentences. Registry value facts
require their containing key evidence to be disclosed too. A shortened field remains
a shortened reported value, not the complete original payload.

Relationships and detections are selected by IDs assigned to actual engine objects.
Their original reasons, limitations, evidence IDs and statuses remain unchanged.
`CONFIRMED` and `LIKELY` remain distinct inside deterministic-correlation results;
`CORROBORATED` is separate; weaker/ambiguous statuses remain explicitly unresolved.
Similarity scores cannot become these objects or statuses. A detection is not proof
of compromise. Semantic retrieval labels describe selection, not machine facts.

Free model prose is accepted only in clearly unverified hypotheses with disclosed
citations and at least one alternative, or in model-proposed unknowns. These are not
validated factual claims. `ANSWER_SUPPORTED` describes structural validation of
disclosed findings, not scientific accuracy, authenticity, causation or completeness.
On failure or limits, Locard produces a controller-rendered partial result and an
explicit termination reason, rather than inventing a final model answer.

## Budgets and termination

Every model iteration consumes one step, including malformed or ungrounded
responses. This bounds retries and loops. `requested_calls` counts decoded
`action: tool` proposals; invalid final answers can therefore consume steps and
increment `rejected_requests` without incrementing `requested_calls`. Repeated
calls, call-budget limits, analyst refusals and worker execution failures retain
their existing separate termination/counter behavior.

DEBUG proposal diagnostics include investigation ID, step/proposal sequence,
tool-call number when applicable, canonical tool name (or `unknown`), argument
SHA-256, category, validation stage and a bounded deterministic reason. They do
not log argument values, evidence payloads or raw model responses. Existing
`rejected` transcript events and tool-call manifest entries also carry diagnostic
metadata, using the same chain and audit linkage; no extra audit events are emitted.
Existing transcripts remain sensitive derived data and retain their existing
bounded request/reason fields.

Categories distinguish unknown tools, malformed proposals, invalid/unknown
arguments, unexposed anchors, final grounding violations, repeated calls,
scope/policy/budget refusal, and other validation failures. Source/host ambiguity
detected by an approved worker is logged at `worker_execution`; it remains a
tool failure rather than being reclassified as a rejected proposal. An ID from
another case is rejected as `UNEXPOSED_EVIDENCE_ID`: the exposure ledger cannot
establish that it belongs to another case, and diagnostics do not open other cases.

The termination DEBUG line includes all four counters. The historical
3-step/1-requested/1-accepted/2-rejected result alone cannot establish the exact
rejection causes. New records expose the causal sequence; guidance gaps should
be assessed from those records without loosening validation.

Interactive activity uses fixed phase labels relayed from the controller/worker
to the terminal-owning parent: preparation, fingerprint calculation, initial
retrieval, exposure preparation, local-model wait, proposal validation, approved
read-only execution and finalization. The activity line clears before approval
input and resumes only on a subsequent work phase. Dry-run never displays a
proposed-tool execution phase. Fingerprinting during final state validation may
display the fingerprint label again.

Animation is disabled when investigation DEBUG logging is enabled so diagnostic
lines remain readable. To start an interactive session with diagnostics:

```powershell
.\.venv\Scripts\python.exe -c "import logging; from forensic_assistant.cli import main; logging.basicConfig(level=logging.WARNING, format='%(message)s'); logging.getLogger('forensic_assistant.investigation_ai').setLevel(logging.DEBUG); raise SystemExit(main())"
```

Choose the case, then run:

```text
investigate-ai --approve-tools --max-tool-calls 2 --max-steps 3 "Did coreupdater.exe execute after loot.zip was downloaded?"
```

This is a separate diagnostic run from visual animation acceptance.

CLI overrides exist for iterations, calls and full runtime. Prompt bytes count
system/user content, not HTTP serialization or model-specific chat templates; the
server must have adequate context for its template and grammar. The separate grammar
has its own bound. Model identity is the server-reported name, not an attestation of
the weights; reported token counts are retained where available. Thinking is disabled,
temperature is 0.2 and top-p is 0.95. Private chain-of-thought is not stored.

Canonical equivalent calls are not rerun against the same fingerprint. Three
consecutive accepted operations without a new original ID stop the loop; new fields
on an old ID do not count as new evidence. Repeated empty searches and oscillating
calls are covered by these controls. Terminal codes include `ANSWER_SUPPORTED`,
`INSUFFICIENT_EVIDENCE`, `NO_NEW_EVIDENCE`, `TOOL_LOOP`, `TOO_MANY_REJECTIONS`,
`BUDGET_EXHAUSTED`, `MODEL_FAILURE`, `TOOL_FAILURE`, `USER_SCOPE_REACHED`,
`EVIDENCE_STATE_CHANGED` and `SEMANTIC_STATE_CHANGED`. WAL pressure is a recorded
resource-limit reason. No stop code proves the machine clean or compromised.

## Snapshot validation gate and chosen consistency model

The full-investigation SQLite snapshot was **rejected**. In the synthetic gate,
two readers retained an initial one-row snapshot while a writer added 1,536 rows
in 24 commits. Maximum commit latency was 0.041 seconds, but the WAL retained
102,254,312 bytes; a passive checkpoint advanced only 3 of 24,819 frames. This
exceeded the proposed 64 MiB allowance while waiting for model responses. A held
rollback-journal reader also blocked writer commits. Normal reader exit followed
by forced termination of the second reader released locks; a test-writer checkpoint
truncated WAL to zero in under 0.5 seconds.

The earlier replacement used **per-operation fingerprint validation**: initial
retrieval, every approved tool, and completion each recomputed the exact content
fingerprint in the same read transaction as the operation. This released live-case
locks between turns, but a one-tool investigation hashed the entire case three times.

The current approved design uses a **private temporary SQLite backup** per
investigation. SQLite's backup API copies a transactionally consistent view,
including committed WAL content. The live read transaction ends after copying;
Locard does not hold it during model responses or tool execution. The original
full content fingerprint F0 is computed from that copy. Every bounded tool opens
that same private copy with the existing read-only opener, authorizer, SQL limits,
deadlines and grounding/authorization checks. No tool reads the live case.

At completion Locard computes the live case's full content fingerprint again and
compares it to F0. A mismatch rejects the proposed final answer and stops with
EVIDENCE_STATE_CHANGED. If equality cannot be checked (for example cancellation or
timeout), results explicitly cover only the original snapshot. F0 is never replaced.
This detects changes at completion, rather than before each tool; it does not
monitor changes after the final check. No mtime, row-count shortcut or cross-run
fingerprint cache substitutes for content validation. Semantic index freshness
uses the same exact F0 only through an internal proof bound to the active pinned
snapshot connection; normal semantic searches still perform their full check.

The supervisor creates a random private temporary directory, never selected by
the model. On Windows its protected ACL grants access only to the current user and
SYSTEM; the worker pins the copy against writes/replacement. Reparse/symlink
redirection is rejected. The copy is derived temporary data, not evidence or
provenance, and requires approximately the case's size in free temporary disk.
After stopping workers the owner removes it on success, rejection, cancellation,
timeout and failures. Unconfirmed cleanup surfaces CLEANUP_LIMITATION. No checkpoint
is issued against the live case. Read-only SQLite can access WAL/SHM coordination
files; the guarantee is no evidence row/schema/source modification, not zero OS I/O.

Focused tests cover a WAL writer committing during backup (the copy retains the
original read view), released-reader checkpoint cleanup, mutation detection, exact
F0 preservation, no cross-case/run reuse, Windows private permissions, write pinning,
reparse rejection, timeout/cancellation, and abnormal controller termination.

Synthetic scale measurements (1,114,791,936-byte case; mocked model, real workers,
semantic retrieval disabled; one measurement per variant):

| Run | Full hashes before/after | Hash seconds before/after | Total seconds before/after |
| --- | --- | --- | --- |
| Dry-run | 2 / 2 | 66.35 / 67.24 | 68.25 / 73.16 |
| One approved tool | 3 / 2 | 102.32 / 68.72 | 104.39 / 85.80 |

Copy creation took 4.06 seconds in the dry-run and 14.89 seconds in the one-tool
run, using 1,114,791,936 bytes each. All four fingerprints were identical. Dry-run
pays the copying cost without reducing hash count. Timing varies with disk/cache
conditions; these measurements do not establish Standard2 performance.

The model prompt now distinguishes exposed IDs from disclosed leaf values and
instructs retrieval before finalizing when needed fields are absent or truncated.
An unresolved answer is valid. Validators, disclosure limits, allowlists, approval,
step accounting and rejection budgets are unchanged. Interactive human output adds
a concise Locard-generated notice when final grounding rejections occur without a
supported conclusion; minor malformed proposals remain quiet. The notice uses
controller counts and fixed reasons, never model prose. Explicit --json and
non-interactive output remain pure structured output. Additive state diagnostics
record final-grounding rejection counts/reason tags; metrics.integrity records
hash/copy timings, copy size and live-case equality. Evidence and transcript chain
semantics are unchanged.

## Transcripts, privacy and replay

Each investigation has an exclusively created UUID directory, an atomic manifest and
bounded append-only JSONL events, flushed to disk. They record the objective, policy
and source-code fingerprint, case content fingerprint/schema, initial retrieval,
semantic generation/model identity when used, disclosed compact fields, validated
requests/reasons, controller decisions, results, metrics, omissions and termination.
Malformed responses are represented by a digest and bounded relevant request fields,
not arbitrary hidden reasoning. File hashes/chains detect accidental modification;
they are **not signatures or authentication** against a party who can rewrite files.
An interruption can leave a visibly incomplete transcript; do not treat it as complete.

`show` reads bounded JSON and labels it recorded/untrusted. A bounded read-only
fingerprint check reports whether the selected case matches, or why it cannot be
checked; it does not revalidate every recorded finding. `replay` checks the current code/policy/schema/rule registry,
original evidence fingerprint and semantic identities, revalidates all accepted
operations and exposed support, and executes only the fixed read-only adapters.
It does not call the language model or execute transcript strings. Changed or
incompatible state is refused. A separate UUID transcript records comparisons;
the original is untouched. Reproduction of outputs is not reproduction of reasoning
or proof of truth. A binary/library upgrade or platform difference may prevent an
exact match even when useful evidence remains unchanged.

Transcripts contain objectives, IDs, paths, users, evidence excerpts and hypotheses.
Protect them like the source case; do not commit or publish real runs. The repository
uses a default-deny extension allowlist plus explicit transcript/index/database/model
exclusions. V4 creates no public telemetry or automatic downloads. Embedding setup,
if needed, remains the separate explicit V3 setup operation. Repository fixtures are
generated synthetic examples; integration output belongs outside the repository.

## Validation and limits

Run the ordinary accumulated suite without MiniCPM:

```powershell
python -m pytest -q -p no:cacheprovider --basetemp C:\Temp\locard-tests-unique
```

Use fresh output directories for explicit synthetic integration checks:

```powershell
python tests\v4_semantic_validation.py C:\Temp\locard-semantic-check --model-path data\semantic-models\bge
python tests\v4_model_validation.py C:\Temp\locard-model-check --endpoint http://127.0.0.1:8080
```

The first requires the V3 optional semantic environment and a previously installed
local model. The second requires an operator-started llama.cpp server and exercises
a real structured tool request and final finding. Neither runs in ordinary pytest.
Synthetic scripted comparisons measure evidence discovery, bounds and validation;
they do not establish autonomous investigation quality or forensic accuracy. See
[validation results](VALIDATION.md). Prompt injection can still steer permitted
searches, omit useful investigation paths or produce poor hypotheses. Human review,
original artifacts, acquisition provenance and domain expertise remain necessary.
